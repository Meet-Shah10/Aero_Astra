## 1. Quick start

```bash
cd aero_astra
python3 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt
export OPENROUTER_API_KEY="your_key_here"
```

**Before you do anything else, confirm the model loads:**
```bash
python3 -c "import joblib; joblib.load('backend/models/sentinel_production.pkl')"
```
If this throws a pickle/unpickling error, the file is a broken git-lfs pointer stub (see §5) — re-run `python backend/sentinel/train.py` from repo root to regenerate it from the real local training data before doing anything else. It takes about 15 seconds.

**Then confirm the simulator runs:**
```bash
python3 -c "
from backend.simulator import simulate_scenario
r = simulate_scenario(fault='tcs_thermal_runaway', severity=0.7, duration=600, dt=10, seed=1)
print(len(r.frames), 'frames,', r.frames[-1].state.tcs.panel_temp, '°C final panel temp')
"
```
Expect ~5 frames printed... actually 61 frames (duration/dt + 1), panel_temp climbing from ~38°C toward the mid-50s°C at 600s into a 90s-ramp fault.

## 3. Which faults are demo-safe right now

Verified by running `simulate_scenario()` and scoring the output, not by reading the fault descriptions:

| Fault | Demo-safe today? | Why |
|---|---|---|
| `tcs_thermal_runaway` | ✅ Yes | panel_temp 38°C→76°C in ~40 min at severity 0.7 — crosses both warn (55°C) and approaches critical (80°C) |
| `ttc_signal_dropout` | ✅ Yes | signal_strength crashes to -114.7 dBm, past mission-loss (-115 dBm) |
| `propulsion_thruster_fault` | ✅ Yes | thruster_temp redlines to 200°C (hard clamp), fastest onset of any fault |
| `eps_battery_degradation` | ❌ Not yet | bus_voltage barely moves in 1hr (28.80V→29.87V, *up*, not down); SOC needs ~4hrs to visibly degrade |
| `adcs_reaction_wheel_degradation` | ❌ Not yet | attitude_error moves 0.50°→0.83° in 1hr, nowhere near the 5° warning line |
| `eps_cascade_power_failure` | ❌ Not yet | despite being "complete solar array loss," bus_voltage only reaches 28.08V after 1hr (25V is the warning line); needs ~4hrs |

**If you want to re-tune the bottom 3** (stretch goal, not MVP-blocking): the fix is in `backend/simulator/faults.py`'s modifier magnitudes for `eps_capacity_factor`, `eps_solar_factor`, `adcs_wheel_efficiency`, etc. — they're too conservative relative to how `transitions.py` lets battery SOC / attitude error respond. After changing them, **re-run `run_monte_carlo` and sanity-check the outcome distributions** — these same constants feed ORACLE's Monte Carlo, so a change here can silently shift ORACLE's safety scores too. Don't do this in the last hour before a demo.

## 4. Backend build order

### Phase 1 — `backend/api.py` (blocks everything, do this first)

```python
from fastapi import FastAPI, WebSocket
from backend.simulator.engine import simulate_scenario
from backend.sentinel.engine_b import combined_score
from backend.sherlock.agent import SherlockAgent
from backend.sherlock.simulator_provider import SimulatorTelemetryProvider
from backend.oracle.agent import run_oracle
from backend.oracle.schemas import OracleRequest

app = FastAPI()

@app.post("/trigger")
async def trigger(fault: str, severity: float = 0.7):
    ...  # kick off simulate_scenario, stream frames over the WS connection

@app.post("/approve")
async def approve(request_id: str, approved: bool):
    ...  # unblocks a MANUAL_INTERLOCK action waiting on a human click

@app.websocket("/ws/mission")
async def ws_mission(websocket: WebSocket):
    ...  # streams every message type in §5 as the pipeline runs
```

Loop shape per triggered scenario: stream `telemetry` messages as `simulate_scenario` frames are produced → run `combined_score()` on each frame → on first fire, send `sentinel_alert` → call SHERLOCK with `SimulatorTelemetryProvider(state)` → send `sherlock_diagnosis` → call `run_oracle()` → send `oracle` → run `guardian_decide()` (§4.2) → send `guardian` → if `requires_human_approval`, wait for `POST /approve` before proceeding; otherwise proceed immediately.

**Cache one full real response set per MVP fault as static JSON** (telemetry+alert+diagnosis+oracle+guardian) and serve it with a `[CACHED]` flag if the LLM call is slow/down mid-demo. This is cheap insurance, do it before the demo, not during.

### Phase 1.5 — `backend/guardian.py` (small, rule-based, build alongside api.py)

This is the two-path (three-tier) logic the whole MVP demo hinges on:

```python
SAFE_MODE_THRESHOLD_MIN = 5

def guardian_decide(diagnosis, oracle_response):
    """diagnosis: SherlockDiagnosis: oracle_response: OracleResponse"""
    if diagnosis.time_to_critical_estimate_minutes < SAFE_MODE_THRESHOLD_MIN:
        return {
            "tier": "AUTONOMOUS_SAFED",
            "auto_executes": True,
            "requires_human_approval": False,
            "action": "shed_nonessential_load",  # cheapest, safest, most reversible — not necessarily ORACLE's best_action
        }
    if diagnosis.urgency in ("HIGH", "CRITICAL"):
        return {
            "tier": "MANUAL_INTERLOCK",
            "auto_executes": False,
            "requires_human_approval": True,
            "action": oracle_response.best_action,
        }
    return {
        "tier": "AUTOMATED_GUARDED",
        "auto_executes": True,
        "requires_human_approval": False,
        "action": oracle_response.best_action,
    }
```

Real spacecraft framing for the `AUTONOMOUS_SAFED` tier: this is standard FDIR (Fault Detection, Isolation, Recovery) doctrine — when something crosses a genuinely dangerous line, real satellites don't wait for a full diagnosis or human sign-off, they immediately switch to a conservative "Safe Mode" posture, then reason carefully afterward. `time_to_critical_estimate_minutes` is a real field SHERLOCK already outputs (`backend/sherlock/schemas.py:166`) — this tier is the one piece of logic that turns that field from decoration into an actual decision.

## 6. Known gotchas (each of these cost real time tonight — don't rediscover them)

- **No `.gitattributes`, git-lfs not installed, but 4 files in `backend/models/` look like lfs pointers.** They're dead text files, not tracked lfs objects — `git lfs pull` won't fix them because lfs was never actually wired up. The only fix is regenerating locally (`train.py`) or getting a real copy from whoever has one.
- **`backend/models/` and `backend/results/` are gitignored.** This is correct — don't try to force-add them. It means every machine running the demo needs these files copied in manually (zip + AirDrop/USB/Slack), not pulled via git.
- **`roadmap.md`'s original battery_temp thresholds (35/40/45°C) false-positive on this simulator.** Nominal orbital thermal cycling alone swings battery_temp up to 41.4°C with zero fault active. `engine_b.py` already has the recalibrated values (44/48/52°C) — pull thresholds from there, don't copy the old table.
- **`openai` package version conflicts with system `aiohttp`** in some environments (a `httpx_aiohttp` vendored-transport issue surfaced during testing). If `from openai import OpenAI` throws an `AttributeError` about `SocketTimeoutError`, pin `openai<1.55` or update `aiohttp` to match.
- **`sentinel_production.pkl` alone is not a working detector for the demo faults.** Always route through `combined_score()` in `engine_b.py`. This is the single most important thing in this document — it's the difference between the demo working and SENTINEL silently never firing.
- **sklearn will warn (not fail) about version mismatch** loading the `.joblib` files (trained under 1.7.2, likely running under something newer). Harmless, ignore it.

## 7. Testing checklist before you hand anything back to frontend

```bash
# 1. Model loads and fires on the 3 MVP faults
python3 -c "
from backend.simulator import simulate_scenario
from backend.sentinel.engine_b import score_state
for fault in ['tcs_thermal_runaway', 'ttc_signal_dropout', 'propulsion_thruster_fault']:
    r = simulate_scenario(fault=fault, severity=0.7, duration=3600, dt=10, seed=42)
    best = max((score_state(f.state) for f in r.frames), key=lambda x: x['score'])
    print(fault, best['score'], best['worst_param'])
"
# expect: score >= 0.5 for all three, nonzero score for genuinely varying worst_param

# 2. Nominal run does NOT false-positive
python3 -c "
from backend.simulator import simulate_scenario
from backend.sentinel.engine_b import score_state
r = simulate_scenario(fault=None, duration=3600, dt=10, seed=42)
best = max((score_state(f.state) for f in r.frames), key=lambda x: x['score'])
print(best)
"
# expect: score == 0.0

# 3. SHERLOCK bridge produces a real snapshot
python3 -c "
from backend.simulator import simulate_scenario
from backend.sherlock.simulator_provider import SimulatorTelemetryProvider
r = simulate_scenario(fault='tcs_thermal_runaway', severity=0.7, duration=600, dt=10, seed=1)
p = SimulatorTelemetryProvider(r.frames[-1].state)
print(p.get_subsystem_snapshot('TCS'))
"

# 4. ORACLE runs end to end (needs no fault-specific setup, uses fallback ranking mode)
python3 -c "
from backend.oracle.agent import run_oracle
from backend.oracle.schemas import OracleRequest

r = simulate_scenario(fault='tcs_thermal_runaway', severity=0.7, duration=600, dt=10, seed=1)
```
